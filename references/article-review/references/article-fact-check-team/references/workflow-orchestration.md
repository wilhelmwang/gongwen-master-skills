# 工作流编排规则 V3.1

> 本文档定义"文章核查专家团"6 阶段流程的详细编排规则、阶段衔接逻辑和异常处理机制。
>
> **V3.1 更新**：在 Phase 2 中嵌入了原子声明分解 → 组件级信任评分 → 自适应缺口填补 → 组间一致性交叉验证的子流程；新增 Phase 2.5 声明-证据关系图谱构建。

---

## 1. 前置判断（启动前）

在建立团队前，主理人需快速确定：
1. **文章是否可用**：用户提供的 URL 或全文是否完整
2. **文章类型**：决定是否执行投资风险检测
3. **分析深度**：完整深度分析 / 部分分析

### 文章类型 → 执行路径

| 文章类型 | 执行阶段 | 跳过 |
|---------|---------|------|
| 股票/投资/财经分析类 | Phase 1→2→3→4→5(含风险检测)→6 | 无 |
| 社会/时政/科普/行业分析类 | Phase 1→2→3→4→5(不含风险检测)→6 | Phase 5 风险检测 |
| 非分析类（通告/声明） | Phase 1 概述 + Phase 5 基本评估 | Phase 2/3/4/5 风险检测 |

---

## 2. Phase 1：建立团队 + 内容提取与声明标记

### 目标

完成三件事：建立团队、获取文章内容、结构化标注。

### 编排流程

```
Step 1.1: 主理人判断文章类型
    ↓
Step 1.2: 主理人执行 TeamCreate("article-fact-check")
    ↓
Step 1.3: 主理人 Spawn "content-data-verifier"
    下发任务指令，附上文章 URL/全文 + 前置判断结果
    ↓
Step 1.4: content-data-verifier 执行第一阶段工作
    ├── 如为 URL → WebFetch 获取内容（含三级 fallback）
    ├── 提取基本信息卡片
    ├── 提炼原文核心观点（格式：本文主张/认为……）
    ├── 标注 Toulmin 论证组件（2-3 个核心段落）
    └── 提取 6 类关键声明（编号 声明 #1..#N）
    ↓
Step 1.5: content-data-verifier 回传 Phase 1 产出给主理人
    ↓
Step 1.6: 主理人通报用户："Phase 1 完成：内容已提取，共识别 N 条声明"
```

### 异常处理

| 异常 | 处理 |
|------|------|
| WebFetch 抓取不完整 | 依次执行三级 fallback |
| 文章 < 500 字 | 尝试 WebSearch 补充，仍不足提示用户粘贴全文 |
| 用户仅提供标题 | 提示"需提供 URL 或全文，仅标题无法分析" |
| 非适用文章类型 | 提示"本分析仅适用于分析类文章" |

---

## 3. Phase 2：数据核查与验证

### 目标

对 Phase 1 提取的声明逐条验证，输出经过交叉验证的数据结果。

### 编排流程

```
Step 2.1: 主理人将 Phase 1 完整产出转发给 content-data-verifier
    附指令：继续执行第二阶段——数据核查与验证
    ↓
Step 2.2: content-data-verifier 执行数据核查（V3.1 增强版）
    ├── [V3.1] 原子声明分解：将复合声明拆解为原子级可验证事实
    ├── 逐条交叉验证（每条声明至少 2-3 个独立来源）
    │   ├── WebSearch 查证
    │   ├── MCP 工具验证（如可用）
    │   └── 多源比对
    ├── [V3.1] 组件级信任评分：为每条原子声明绑定独立的信任评分
    ├── [V3.1] 自适应缺口填补：
    │   ├── 第 1 轮：标准搜索（通用关键词）
    │   ├── 第 2 轮（如需）：精化搜索（+时间/地域限定）
    │   └── 第 3 轮（如需）：深度搜索（MCP + 官方库）
    ├── 标注核查结果 + 置信度
    ├── [V3.1] 组间一致性交叉验证：检查声明间的数值/逻辑/术语一致性
    ├── [V3.1] 来源时效衰减：应用时间衰减系数调整星级
    ├── 数据趋势对比（关键指标）
    └── 来源质量星级评估 + 五维矩阵评估
    ↓
Step 2.3: content-data-verifier 回传 Phase 1+2 完整产出给主理人
    ↓
Step 2.4: 主理人通报用户："Phase 2 完成：N 条声明已核查，M 条有误，K 条经过缺口填补"
```

### 核查优先级

| 优先级 | 声明类型 | 核查方法 |
|--------|---------|---------|
| 🔴 高 | 数字型声明的核心数据 | 多源交叉验证 + 官方来源优先 |
| 🟡 中 | 事件性、引用性声明 | WebSearch 查证 + 原文核对 |
| 🟢 低 | 因果性、类比性声明 | 逻辑判断（移交 Phase 3） |

---

## 4. Phase 3：逻辑分析与谬误检测

### 目标

对文章的逻辑结构进行系统审查，检测谬误并执行分析者偏见自检。

### 编排流程

```
Step 3.1: 主理人 Spawn "logic-fallacy-analyst"
    下发任务指令，附上 Phase 1 的 Toulmin 标注 + Phase 2 的核查数据
    ↓
Step 3.2: logic-fallacy-analyst 执行逻辑分析
    ├── Toulmin 组件审查（Warrant/Grounds-Claim/Qualifier/Rebuttal）
    ├── 三阶段谬误检测（筛查→归类→定位）
    ├── 信息完整性检查
    ├── 认知偏见自检（7 项）
    └── 逻辑强度总评（5 维度 ★ 评级）
    ↓
Step 3.3: logic-fallacy-analyst 回传完整产出给主理人
    ↓
Step 3.4: 主理人通报用户："Phase 3 完成：已识别 N 个逻辑缺陷"
```

### 信息隔离规则

- 逻辑与谬误分析师**只接收** Toulmin 标注表和声明核查数据
- **不接收**核查员的判断结论，避免暗示
- 以"盲审"模式独立完成逻辑分析

---

## 5. Phase 4：事实研判与预判

### 目标

基于已验证的数据和逻辑分析，对文章核心观点给出独立的事实判断。

### 编排流程

```
Step 4.1: 主理人 Spawn "fact-judgment-analyst"
    下发任务指令，附上 Phase 2 核查数据 + Phase 3 逻辑分析结果
    ↓
Step 4.2: fact-judgment-analyst 执行事实研判
    ├── 识别研判焦点：从核心观点中提取最需判断的焦点问题
    ├── 独立数据采集：通过 WebSearch/MCP 获取独立数据
    ├── 数据对比分析：文章观点 vs 实际数据
    ├── 形成判断：同意/修正/反驳/数据不足
    ├── 如适用：趋势预判（含不确定性标注）
    └── 结论前置：判断结论放在输出最前
    ↓
Step 4.3: fact-judgment-analyst 回传完整产出给主理人
    ↓
Step 4.4: 主理人通报用户："Phase 4 完成：核心观点研判结论已生成"
```

### 研判红线

| 红线 | 违规示例 | 正确做法 |
|------|---------|---------|
| 无数据不判断 | "这个观点看起来是对的" | "根据 {数据来源}，该观点与实际情况一致" |
| 事实与预判不混同 | "未来一定涨" | "基于当前趋势，未来初步预测为 {方向}，不确定性因素包括 {列举}" |
| 数据不足不硬猜 | "虽然没有数据但我推断..." | "该主张缺乏足够数据支撑，标注为数据缺口" |

---

## 6. Phase 5：风险检测与评分

### 目标

执行投资风险检测（可选）、7 维加权评分、可信度评级。

### 编排流程

```
Step 5.1: 主理人 Spawn "risk-scoring-evaluator"
    下发任务指令，附上 Phase 2+3+4 的完整产出
    如非金融投资类文章，明确标记"跳过风险检测"
    ↓
Step 5.2: risk-scoring-evaluator 执行评分
    ├── 如是金融投资类 → 执行投资风险检测
    │   ├── 利益冲突识别
    │   ├── Pump-and-Dump 信号检测
    │   ├── 情绪操纵分类
    │   └── 合规性检查
    ├── 7 维加权评分（逐维打分 + 置信度标记）
    ├── 声明汇总（✅/⚠️/❌/❓ 分类统计）
    ├── 综合可信度评级
    ├── 使用建议生成
    └── 分析局限性记录
    ↓
Step 5.3: risk-scoring-evaluator 回传完整产出给主理人
    ↓
Step 5.4: 主理人通报用户："Phase 5 完成：综合评分已生成"
```

### 评分速查

| 维度 | 权重 | 速查方法 |
|------|------|---------|
| 事实准确性 | 25% | Phase 2 的 ✅/⚠️/❌ 分布决定 |
| 逻辑严谨性 | 25% | Phase 3 的谬误数量和严重度决定 |
| 信息来源质量 | 15% | Phase 2 的星级评估决定 |
| 框架创新性 | 10% | 文章是否有增量洞见 |
| 信息时效性 | 10% | 发布时间与事件时间差 |
| 生产透明度 | 10% | 作者背景和利益冲突披露 |
| 可读性/结构性 | 5% | 结构和表达质量 |

## 7. Phase 6：报告编译与输出

### 目标

将所有角色产出编译为结论前置的结构化 Markdown 报告，落盘输出。

### 编排流程

```
Step 6.1: 主理人 Spawn "report-compiler"
    下发任务指令，附上所有 5 个角色的完整产出
    ↓
Step 6.2: report-compiler 执行报告编译
    ├── 提取事实研判结论置于最前
    ├── 编译"原文观点 vs 核查结论"对比表
    ├── 整理核心发现（3-5 条）
    ├── 按标准模板组织各章节
    ├── 嵌入免责声明
    └── 生成完整 Markdown
    ↓
Step 6.3: report-compiler 回传报告给主理人
    ↓
Step 6.4: 主理人确认报告完整，写入 deliverables
    ↓
Step 6.5: 主理人通知用户报告路径
```

### 报告结构（结论前置）

```
1. 事实研判结论 ← 置于最前
2. 原文观点 vs 核查结论对比表
3. 核心发现（3-5 条）
4. 数据核查详情
5. 逻辑分析与谬误检测
6. 投资风险检测（如适用）
7. 七维评分矩阵
8. 使用建议
9. 分析局限性
10. 免责声明
```

## 8. 阶段衔接逻辑

### 信息传递表

| 阶段 | 输入 | 来源 | 输出 | 去向 |
|------|------|------|------|------|
| Phase 1 | URL/全文 | 用户 | 信息卡片+观点+Toulmin+声明 | → 主理人 → Phase 2 |
| Phase 2 | Phase 1 产出 | 主理人（来自 Phase 1） | 核查表+趋势对比+来源评估 | → 主理人 → Phase 3/5 |
| Phase 3 | Phase 1 Toulmin + Phase 2 核查 | 主理人 | 谬误报告+偏见自检+逻辑总评 | → 主理人 → Phase 4/5 |
| Phase 4 | Phase 2 核查 + Phase 3 逻辑 | 主理人 | 研判结论+预判+数据缺口 | → 主理人 → Phase 5/6 |
| Phase 5 | Phase 2+3+4 | 主理人 | 风险报告+评分+评级 | → 主理人 → Phase 6 |
| Phase 6 | Phase 2~5 所有产出 | 主理人 | 最终 Markdown 报告 | → 用户 |

### 依赖关系图

```
Phase 1 ──→ Phase 2
  │              │
  │              ↓
  └─────→ Phase 3
              │
              ↓
          Phase 4
              │
              ↓
          Phase 5
              │
              ↓
          Phase 6
```

## 9. 异常处理总则

| 异常场景 | 处理方式 | 影响 |
|---------|---------|------|
| 文章内容无法获取 | 提示用户粘贴全文，暂停分析 | Phase 1 无法完成 |
| MCP 工具不可用 | 降级为 WebSearch 验证 | Phase 2 效率降低 |
| 无独立来源验证声明 | 标记 ❓ 无法验证，注明搜索途径 | 影响事实准确性评分 |
| 文章类型不匹配 | 跳过多余阶段 | 缩短流程 |
| 团队成员异常退出 | 主理人重新 spawn 该成员 | 延长执行时间 |
| 用户中途取消 | 终止流程，清理团队 | 已完成的阶段产出可保留 |

---

## 10. 团队清理规则

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 向所有剩余成员发送 shutdown_request | 优雅关闭 |
| 2 | 等待 shutdown_response | 确保成员已保存产出 |
| 3 | 执行 TeamDelete | 清除团队和任务目录 |
| 4 | 通知用户分析完成 | 附报告路径 |

**注意**：如果会话结束而未执行 TeamDelete，系统会自动清理，不会产生资源泄漏。

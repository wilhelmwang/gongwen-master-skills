# 公文大师 · 专家团写稿手册（team-writing v1.0 · 2026-09-23）

> 团队模式的两条腿之一：`team-orchestration.md` 管**评审**（成品进、意见出），本文件管**写稿**（需求进、成品出）。
> 两者共用同一套主理人契约、信息隔离与门禁规则——差异只在「产出物形态」：评审产出意见，写稿产出正文。
> 所以本文件只写「写稿特有」的部分，通用编排规则不重复，见 `team-orchestration.md`。

## 零、涉密红线（最先看，越界即错）

**多专家写稿必然走 LLM，文本会发往外部端点。涉密材料禁止使用写稿模式。**

涉密材料只能走本地确定性能力（单智能体写作 / 检索 / 排版 / 质检），或由用户改用手工流程。
依据：`gongwen-master` 合规交付·涉密不上网；《保守国家秘密法》（2024 修订）。

采纳任务前先问一句：「这份材料涉密吗？」——若用户答涉密或不确定，**退出写稿模式并说明原因**，不得默默执行。

## 一、为什么公文不能照搬「多视角投票」

投资类专家包的 22 位分析师输出的是**同一个标量**（方向 + 强度），因此可加权平均、可聚合。
**一篇文章是单一文本流**——三份稿无法「平均」成一份；所谓「融合两版」，工程上约等于重写一遍。

由此得**四条铁律**：

1. **并行对象必须降维**。不能并行出稿，只能并行出**更小的单元**（要素、素材、槽位）。
2. **执笔必须单点收敛**。语脉（气口的连贯、排比的递进、首尾的呼应）只在一个人一次写完时才不断。
   多人各写一段再拼起来，拼缝处一定看得出来。
3. **Phase 0 必须停机等确认**（v8.1.1 补）。骨架是全局约束，写偏了全部返工；
   且实跑证明模型会自行"确认"并连做——故用**独立派遣 + 停机标记**在结构上阻断，见三·五。
4. **交付前必须校准篇幅**（v8.1.2 补）。骨架的槽位字数即目标篇幅，**四拓扑通用**——
   T1 无缝合也要核对（v8.1.2 前该条只写在 T2/T4 缝合规则中，T1 流程不含此步），见五·五。

**这与机关实际同构**：现实中公文起草就是一人执笔、多人供料供依据。执笔人把素材吃进去，一次成文。
多视角的价值在**上游**（供什么料、依什么据）与**下游**（谁来挑错），不在执笔本身。

> **与评审模式的对照**：评审模式恰恰相反——它要求多位专家独立审同一稿，分歧越大越有价值（分歧=信息量）。
> 写稿模式里，结构分歧要交用户裁，措辞分歧要由秉笔抹平（写稿的分歧=不统一）。**不要把两套判据混用。**

## 二、四个写稿角色

| 角色 | 定位 | 能力载荷 | 产出 |
|---|---|---|---|
| **秉笔**（总纂） | 定骨架、单点成文、缝合 | `govdoc-*`（文种体例）+ `formulas.md` | 骨架契约 / 成品稿 / 缝合说明 |
| **分笔**（笔手） | 承包一个分论槽位 | 目标文种体例 + 指定文风 | 槽位段落 + 要素来源 |
| 佐笔（复用现有） | 只供料，不执笔 | `据实`（数据）/ `法鉴`（政策依据）/ `笔致`（语料口径） | 要素清单 + 证据锚点 |
| 竞稿者（复用现有） | 各写一版全篇 | `章策`/`城构`/`枢垣`（各绑一种文风） | 完整成稿 |

角色卡实体在 `../agents/`：`秉笔_writer-lead.md`、`分笔_writer.md`；佐笔与竞稿者复用既有角色卡，不另建。

**能力载荷 = 现有技能，零改造**——秉笔拾取 `govdoc-{文种}/SKILL.md` 与 `formulas.md` 作为自身指令，
分笔拾取同一份体例 + 指定文风模块。这与评审模式的角色包机制一致（见 `team-orchestration.md` 第二节）。

## 三、槽位契约（写稿模式的「收口契约」）

写稿模式借用了评审模式最关键的一个设计：**产出必须收口为可复用的固定结构**。
评审的收口是三段意见（判定/证据/可执行修改）；写稿的收口是**槽位契约**——每个槽位交付时按此六项收口：

```
槽位：S2 主体·第一分论
构件：一级标题 + 小帽段 + 2 支撑段
篇幅：600-800 字
证据：数据 1（地方统计年鉴页码）/ 案例 1 / 政策依据 1（文件名+文号）
语脉锚点：上承「……」；下接「……」（首尾各一句，由秉笔填）
状态：成稿 | 【待补：缺什么，向谁确认】
```

**六项缺一不可**，其中三项是硬约束：

- **篇幅**用区间，不用「详细/精炼」这类形容词——它是唯一能让多段拼起来不头重脚轻的量尺。
- **证据**必须带锚点（年鉴页码 / 材料编号 / 文件名文号）。没有出处的证据不许进槽位，改标【待补】。
- **语脉锚点**是缝合的依据。分笔写之前就知道自己这段要接住上段的哪句话，断口才不会失控。

> **为什么不用「信心值」**：投资包要求分析师自报 0-100 信心，用于加权。公文的对应物不是信心，
> 是**篇幅区间 + 证据密度**——公文的「强度」体现在这两处，不体现在自报数字上。

## 三·五、Phase 0 停机规程（v8.1.1 · **结构强制，不靠自觉**）

**为什么单独立此节**：v8.1.0 首次实跑时，秉笔 subagent **跳过了骨架确认**、并**虚构用户确认**
（自称"已确认，落实四项选择"，而用户从未给过选择）。事后确认根因：文档里写了「骨架必确认」，
但**文档约束不等于模型遵守**——只要 Phase 0 与 Phase 1 在同一个子任务里，模型就会一口气做完。

**修法：用结构阻断代替文档约束。** 三条硬规程：

**规程 1：Phase 0 与 Phase 1 必须是两次独立的派遣，不得合并。**
秉笔在 Phase 0 的子任务**只允许输出骨架契约**，任务提示词中必须显式写死：
「你是秉笔。**本次只出骨架契约，不写任何正文、不做佐笔派单、不执行后续阶段**。
输出末尾必须原样打印一行 `【等待用户确认骨架】`，然后结束。」

**规程 2：主理人见到 `【等待用户确认骨架】` 即必须停下，先请用户确认。**
- 未见该行 → 视为 Phase 0 未完成，**打回重做**（这是门禁，不是建议）；
- 见到该行 → 用 AskUserQuestion 呈交骨架，请用户确认或修改；
- **用户确认之前，绝不派遣佐笔/分笔**。任何理由都不构成跳过依据。

**规程 3：禁止代用户确认。**
下列都**不是**用户确认，一律不得据此进入 Phase 1：
用户说了「你看着办 / 随便 / 都行」、模型自行推断「用户应该会同意」、
多轮对话中用户的沉默、以及**任何模型自己写出的"已确认/契约锁定"字样**。
**只有 AskUserQuestion 的返回结果**才算用户确认。

> **自查问句**（每次 Phase 0 结束时过一遍）：
> 我拿到的是**用户的真实回答**，还是**我自己推断/仿写的确认**？—— 若是后者，停下，去问。

**S 级豁免**：单文种短件（如一条通知）不启用写稿模式，无 Phase 0 之说。
判不准时按 S 级处理（走主理人直办），宁可少组队，不可跳过确认。

## 四、四个拓扑

四种都做进路由，由用户按需选（规则 F 的写稿关键词命中后，按关键词判定拓扑；判不准时问一句）。

### T1 主笔 + 佐笔（推荐默认）

**适用**：绝大多数写作请求。语脉风险为零（单点成文），成本适中。

```
Phase 0【秉笔·独立派遣①】只出骨架契约 → 原样打印「【等待用户确认骨架】」→ 结束
        ↓ 主理人见停机标记 → AskUserQuestion 请用户确认（见三·五规程 2/3）
Phase 1【佐笔·并行】按骨架的供料需求，并行拉据实/法鉴/笔致（**仅在用户确认后**）
Phase 2【秉笔·串行】吃料，一次成文（不拼接，整篇一次写出）
Phase 2.5【秉笔·自核】篇幅校准（见五·五节，**四拓扑通用**）→ 偏离 >10% 先补/删
Phase 3【可选】交评审团（场景 1）复核
```

**关键**：Phase 1 的佐笔**只出要素清单，不出正文**。它们产出的是「2024 年 GDP 2300 亿元（年鉴第 X 页）」
这样的可引用条目，由秉笔在一个连续的行文里消化掉。这是 T1 与 T2 的分界。

> **Phase 2.5 不可省**：T1 虽无缝合，篇幅仍需核对（v8.1.2 前 T1 流程不含此步，属路径缺口）。

### T2 分工承包

**适用**：长材料、多分论且彼此独立（如工作报告的几大板块）。成本 H 级。

```
Phase 0【秉笔·独立派遣①】定骨架契约（含每槽语脉锚点）→ 打印「【等待用户确认骨架】」→ 结束
        ↓ 主理人请用户确认（三·五规程 2/3）
Phase 1【分笔·并行】N 位各承包一个分论槽位，按槽位契约交付（**仅在用户确认后**）
Phase 2【秉笔·串行】缝合（见第五节硬约束）
Phase 2.5【秉笔·自核】篇幅校准（见五·五节，**四拓扑通用**）
Phase 3【可选】评审团
```

**风险**：缝合处易拼盘。**只在分论之间本就没有强语脉依赖时用**——若全文需要一气贯通的排比递进，改用 T1。

### T3 多版竞稿

**适用**：风格未定、想让用户看着挑；或重要材料要择优。**成本 ×N**。

```
Phase 0【秉笔·独立派遣①】定硬要求（文种/主题/篇幅/场合），不写骨架
        → 打印「【等待用户确认骨架】」→ 结束
        ↓ 主理人请用户确认（三·五规程 2/3）
Phase 1【竞稿者·并行】N 位各写全篇（章策/城构/枢垣绑不同文风，天然各成一路）（**仅在用户确认后**）
Phase 2【秉笔】择优定稿；用户要融合时，融合按「重写」对待并明说
```

> **T3 的 Phase 0 也不能省**：它出的不是骨架而是**硬要求清单**（文种/主题/篇幅/场合），
> 但同样必须停下来等用户确认——否则多位竞稿者按错误的要求各写一版，浪费是 N 倍的。

**如实提示**：公文语体下「选优」主观性强，且融合多版几乎等于重写。**默认选优不融合**，
除非用户明确要求融合，并接受融合稿的原创性低于单版稿。

### T4 分层混合

**适用**：大型材料（政府工作报告级），骨架需要集思广益、主体可分包。**成本 H+**。

```
Phase 0a【骨架会战·并行】多专家各出骨架方案
Phase 0b【秉笔·独立派遣①】裁定统一骨架 → 打印「【等待用户确认骨架】」→ 结束
        ↓ 主理人请用户确认（三·五规程 2/3）
Phase 1【分笔·并行】主体分论承包（**仅在用户确认后**）
Phase 2【秉笔·独写】开头、结尾、过渡段（语脉最吃功夫处，绝不外包）
Phase 3【秉笔】缝合
Phase 3.5【秉笔·自核】篇幅校准（见五·五节，**四拓扑通用**）
Phase 4【可选】评审团
```

> **T4 的 0a 与 0b 必须分成两次派遣**：会战专家只出方案、不裁定；秉笔裁定后**即停**等确认。
> 若合成一次，模型会连着派笔手——这正是 v8.1.0 实跑踩到的坑。

**设计意图**：把「最需要单点控制」的骨架、首尾、过渡全部留给秉笔，只把最容易被切分的分论外包。
这是「并行对象降维」原则在大型材料上的极限用法。

### 拓扑速查

```
含「一起写稿/团队写稿/多人合写/专家团写稿」        → T1
含「分段承包/分段写/分头写/分工写」                → T2
含「各写一版/竞稿/多版选优/写几版挑一版」          → T3
含「全程合写/骨架会战/分层合写」                    → T4
命中写稿但拓扑不明                                  → 问一句，默认 T1

四拓扑共同铁律：
  ① Phase 0 独立派遣、必打印停机标记、必等用户确认（见三·五）；
  ② 交付前必做篇幅校准（见五·五）——含 T1，不限缝合场景。
```

## 五、缝合规则（T2/T4 硬约束）

缝合不是拼接。以下四条按顺序执行，**任一不达标不得交付**：

1. **过渡句必须重写**。相邻槽位之间的衔接句由秉笔重新写出，**禁止**直接前后拼接原文。
2. **语脉锚点校验**。逐对检查「上段末句 → 下段首句」能否连读；读不通就改下段首句，不改上段末句（保持已认可部分）。
3. **段落撞车检测**。两位分笔可能撞车（都写了同一条数据、同一个案例）。逐段比对，撞车的保留一处、
   另一处换证据或删；**不得两处都留**（重复在公文里是硬伤）。
4. **口径统一**。术语、机构简称、领导称呼、时间表述全文统一，由秉笔一处裁定、全篇照改，
   改动清单随交付附上。

> 篇幅校准原为本节第 5 条，v8.1.2 起**独立成节并扩为四拓扑通用**（见下节）——
> 它曾在 T1 单点成文时失效：该条只写在缝合规则里，而 **T1 无缝合、整套规则不适用**，
> 篇幅遂无人核对（v8.1.2 实跑发现的路径缺口）。

**缝合说明随交付附上**（≤10 行）：改了哪几处过渡、撞车如何处理、口径统一了哪些词。用户据此判断是否照单全收。

---

## 五·五、篇幅校准（**四拓扑通用硬约束** · v8.1.2 提级）

**适用所有拓扑，含 T1**。它不是缝合的一部分，是**交付前的独立校验**。

**为什么单立**：骨架的槽位字数区间逐槽相加 = 全文目标篇幅，这是骨架契约的一部分，
**与是否拼接无关**。T1 虽单点成文、无拼缝，但同样需要核对篇幅——而 v8.1.2 前该条只写在
T2/T4 的缝合规则里，**T1 流程根本不含此步**（路径缺口，非模型不遵守）。

**执行规程（秉笔在成文后、交付前必做）**：

0. **用工具统计，不要手算**（v8.1.4 新增）：
   ```bash
   python wordcount.py <稿子.md> --range <下界> <上界>
   ```
   `wordcount.py` 是本包唯一的篇幅统计实现，已把口径与正文边界固化进代码。
   **实测教训**：口径只写在文档里的那三轮，同一篇稿子算出了 4256/2799、8592/8660/8542 三组不同数字，
   每次都要人工排查**是模型报错还是口径不同**——浪费整整三轮往返。**用工具即无此问题**。

1. **统计实际字数**——**口径必须显式声明**，否则会出现"同一篇稿子两个字数"的争议。
   本包统一采用**非空白字符数**（含中文、数字、字母、标点，不含空格与换行），
   即公文语境下的"字数"（与 Word「字符数（不计空格）」同口径）。
   正文边界**以 HTML 标记为准**：稿子必须含 `<!-- 正文起 -->` 与 `<!-- 正文止 -->`，
   二者之间即正文，**含主送机关行与落款单位行**（它们是公文正文的组成部分）；
   不含外层 H1 报告标题、溯源表、缝合说明。
   > 踩坑记录（三轮）：v8.1.2 因未定义口径，秉笔按"非空白字符"算得 4256（正确），
   > 复核者按"纯中文字"算得 2799，一度误判为"虚报 1457 字"；
   > v8.1.3 又把标题行与说明文字算进去得出 8660（正确值 8592）；同轮还混用过过程版 8542。
   > **同一篇稿子多种口径，最大差 1.5 倍**。故本篇写死口径，并**由 wordcount.py 强制执行**。
2. **与骨架总区间比对**，按偏离幅度处置：

| 偏离 | 处置 |
|---|---|
| 在区间内 | 通过 |
| 低于下界 **≤10%** | 通过（允差）；但在交付说明中标注实际字数与区间 |
| 偏离 **>10%** | **必须补/删**，不得直接交付 |
| 偏离 **>20%** | 视为骨架执行失败，回 Phase 0 复核骨架是否切合实际料情 |

3. **补写方向**（写短时）：优先扩**已有证据支撑的槽位**（把清单里未用完的数据/案例补进去），
   其次补**过渡与承接句**；**禁止**为凑字数加套话、重复表述或空泛议论——那正是"去 AI 味"要反的东西。
4. **删减方向**（写长时）：先删重复表述与冗余修饰，再压缩次要分论；**不得**删掉证据锚点或【待补】标记。
5. **字数记入交付**：缝合说明（T2/T4）或交付说明（T1）中写明「正文实际 N 字 / 骨架区间 A-B 字」。
6. **正文必须打标记**（v8.1.4 新增，写稿模式硬要求）：
   交付件的正文首尾各加一行 HTML 注释——
   ```
   <!-- 正文起 -->
   …正文…
   <!-- 正文止 -->
   ```
   **为什么必须**：无标记时正文边界只能靠推断，而"主送机关算不算、日期行算不算、说明行算不算"
   在推断规则里没有唯一解——四种边界写法在同一份稿子上差 11～50 字符；
   更严重的是多节交付件（如 T3 的"定稿全文"节）会被节标题提前截断（实测只得 647 字，真实值 1567）。
   **标记是把"边界定义"从主观判断变成客观事实**，是消除字数争议的唯一办法。

   **标记位置的四条细则**（v8.1.4 补标记时实测确定）：
   - **标题不计入正文**——外层报告标题（H1）与讲话稿的标题都属"题目"，起标记放在其**之后**。
     （实测：T3 把讲话标题计入得 1582，排除后 1567，与秉笔自报值吻合。）
   - **主送机关计入**——如「地方人民政府：」，是正文的组成部分。
   - **落款单位与日期计入**——如「地方发展和改革委员会」，同属正文。
   - **【待补】标记计入**（它是正文的一部分），但报告时同时给出剔除后的数字，
     以便判断"缺口有多少是标记占位"。
   > 注：`wordcount.py` 的 `<!-- 正文起 -->` 注释后可写范围说明（前缀匹配，不影响识别）。

> **与"不得套话填充"的关系**：本节的"补写"与第六节"不许用套话填【待补】"是两条独立的红线——
> 补写只能补**有依据的内容**；没有依据的内容宁可让篇幅不足并如实报告偏差，也不许编。

> **骨架定区间时同口径**：Phase 0 骨架里各槽位的"篇幅：600-800 字"，也按上述**非空白字符**口径估。
> 秉笔出骨架时若不确定，按"每段大概多少行 × 每行多少字"粗估即可，但**口径必须与交付时的校准一致**——
> 两处口径不同会让校准失效（写着"低于下界"，其实达标）。

## 六、逐段溯源（写稿模式的交付本体）

成稿之后附**写稿溯源表**，把每段追到「谁供的料 / 谁写的 / 依据在哪」。
格式沿用 `govdoc-material/references/provenance-table.md` 的 7 列 schema，把「材料编号」列换成「供料角色」：

| # | 成稿位置 | 要素内容 | 类别 | 供料角色 | 依据锚点 | 状态 |
|---|---|---|---|---|---|---|
| 1 | 帽段 | 2024 年地方 GDP 2300 亿元 | 数字 | 据实 | 地方统计年鉴2025·第X页 | 已办 |
| 2 | 二、重点任务 | 依据《XX 规划》（国发〔2021〕29号） | 提法 | 法鉴 | 政策法规库·文号检索 | 已办 |
| 3 | 三、工作要求 | 二期建设拟于 10 月启动 | 事项 | 用户材料 M2-§3.1 | — | 拟办 |
| 4 | 结尾 | 防汛物资储备量 | — | — | — | **【待补】** |

三列不可省：**依据锚点**（没有就不许进表，进【待补】）、**状态**（已办/在办/拟办，不许把计划写成成效）、
**供料角色**（让用户知道该找谁核对）。

### 缺料处理（继承 `govdoc-material` 红线）

- 不许用估算值填【待补】（「约 1000 万元」比留空更糟，它看起来像事实）。
- 不许用套话填【待补】（「同时也存在一些不足」暗示了未被指认的问题，本身就是失真）。
- 不许静默删除【待补】。

标记写法：`【待补：防汛物资储备量——材料未提供，需向应急局确认】`

## 七、编排契约（写稿模式专用，补齐评审手册未覆盖处）

评审手册 `team-orchestration.md` 第一节写「主理人**不亲自撰写正文**」——**这条只管评审场景**。
写稿场景下必须改写为：

1. **主理人不写正文，秉笔写**。主理人（文衡）仍只编排、判级、门禁、汇签；
   执笔权在秉笔，不在主理人。两个角色的分工不得混。
2. **秉笔是唯一执笔点**。T1 全篇由秉笔写；T2/T4 秉笔写首尾过渡并缝合；T3 秉笔择优定稿。
   **任何方案下正文只经秉笔一人的手**——这是语脉不断的充要条件。
3. **佐笔不越界**。佐笔（据实/法鉴/笔致）只供要素与依据，**不得输出成段正文**。
   一旦某角色既供料又执笔，它就会开始自我审查，把内容磨成中性的四平八稳——这正是评审手册
   「约束与创作分离」要防的事。
4. **骨架必确认——结构强制，非文档建议**（v8.1.1 升级）。秉笔出骨架契约后**必须停机**，
   由主理人经 AskUserQuestion 取得**用户真实回答**才可派工。
   - 执行细则见**三·五 Phase 0 停机规程**（独立派遣 + 停机标记 `【等待用户确认骨架】` + 禁止代确认）；
   - **禁止把「用户沉默 / 模糊授权 / 模型自写的"已确认"」当作确认**——v8.1.0 实跑正是这样漏的；
   - 短件豁免：S 级单文种短件（如一条通知）不启用写稿模式。
5. **信息隔离按拓扑分**：
   - T1/T2/T4：佐笔之间、分笔之间**不需要**隔离（大家服务于同一篇，供料撞车反而便于检测）；
     但分笔**不得**看到其他分笔的成品（防模仿致拼盘）。
   - T3：竞稿者之间**必须**隔离（互不知情），否则会相互趋同，失去「多版」的意义。
6. **门禁与打回**：沿用评审手册——不达标打回 ≤2 轮，仍不达标上报用户。
   写稿场景的验收标准是**五·五篇幅校准 + 第六节溯源表完整性**（T2/T4 另加第五节四条缝合规则）。

## 八、成本纪律与触发

| 级 | 触发 | 拓扑 | 成本 |
|---|---|---|---|
| S | 单文种短件 | **不启用写稿模式**（主理人直办） | 1x |
| M | 命中写稿关键词 + 单文种 | T1 | 3-5x |
| H | T2/T3/T4，或长材料 | T2/T4；T3 另计 ×N | 8-10x+ |
| H+ | 大型材料（报告级） | T4 + 评审团串联 | 15x+ |

**仅显式点名启用**。「你看着办」这类模糊授权**不**进写稿模式——照常走单智能体主路径。
理由：写稿模式成本数倍于直办，误触发代价大；且日常写作本就不需要组队。

**与评审串联**：先写（本文件）→ 再审（`team-scenarios.md` 场景 1）。
串联时秉笔的成稿作为评审输入，评审团照既有流程独立评审，秉笔不参与评审（避免自我审查）。

## 九、本模式不做的事（边界）

- **不做自动「文风融合」**。把三位专家的语感融合成一版，工程上就是重写；本模式不承诺这是「融合」，
  而是明说「择优」或「重写」。
- **不做正文级别的自动合并脚本**。全仓库唯一的近重复检测算法在 `datahub/scripts/corpus/dedup_samples.py`
  （MinHash），但它面向语料管道、且是「只标记不删除」。写稿的缝合是**语义工作**，由秉笔人工完成——
  第四节第 3 条的撞车检测也是人工比对，不假装有脚本能替。
- **不改 sigil 与审稿规则**。评审模式的角色、场景、红线一律不动；本文件是纯增量。
